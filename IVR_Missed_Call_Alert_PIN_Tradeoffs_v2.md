# IVR Missed Call Alert — PIN in Event Payload — Tradeoffs Register (v2)

Companion to `IVR_Missed_Call_Alert_PIN_PRD_v2.md` (v2.0 · 29 Sep 2026 · re-authored in Template v5 from v1.0). Records every decided tradeoff. Not part of the PRD; kept so anyone asking *"why did we pick X?"* has the answer without archaeology.

Rows 1–9 are carried forward verbatim from v1.0's tradeoffs register (11 Sep 2026). Row 10 is new: the v2 re-authoring itself.

| # | Decision point | Chosen | Rejected options | Why (PM's stated reason) | Date |
|---|---|---|---|---|---|
| 1 | Scope of the change | **Narrow event enrichment only** — add `customer_pin` to `dnp_customer_missed_call_alert` and `csp_pin` to `call_dnp_missed_call_alert`; nothing else. | **(a) Full SMS-campaign PRD** — spec the SMS template, DLT copy, delivery rules and CleverTap journey inside this PRD. **(b) Add a new CT event** dedicated to callback-with-PIN. | The SMS campaign is a downstream CRM change that binds to the enriched event — separate concern, separate owner. Reusing the existing two events keeps consumer contracts intact (G1) and lets the SMS spec ship independently. | 2026-09-10 |
| 2 | Which PIN goes where | **Callee's own side** — customer's PIN on the customer event, CSP-side PIN on the CSP event, sourced from the callee-side row in `ivr_pin_registry`. | **(a) Both PINs on both events** — send `customer_pin` AND `csp_pin` on both events. **(b) Caller's PIN** — send the calling side's PIN instead. | The recipient of the SMS is the callee; the PIN they need to dial back is their own. Cross-populating leaks a PIN across sides and confuses downstream binding. The caller's PIN would authenticate the wrong person. | 2026-09-10 |
| 3 | What PIN visibility flag (`ivr_pin_registry.visible`) gates | **Visibility gates the CALL path (IVR vs normal), not the event payload.** If `visible = false`, the call never becomes an IVR call, so these events do not exist for it. Every emission path assumes `visible = true` at Call session start; the flag is not re-checked at emit time. | **Visibility gates the payload** — the event fires under both `visible = true` and `false`, but the PIN field is empty when `false`. (Original v0.1 draft.) | The v0.1 model solved a case that cannot happen — IVR routing already blocks non-visible Tasks from becoming IVR calls. G3 (payload-visibility guardrail), T2 (visible=false transition) and AC-VIS-1/2 were removed in v0.3. Simpler model, one fewer branch, no dead code. | 2026-09-11 |
| 4 | Recipient scope across the Rollover chain plus `retry_count` | **One event per Registered user per Call session, at end of session, only if no one answered.** Alternate and non-registered numbers never receive an event. `retry_count` duplicates in the numbers array never multiply emissions. | **(a) One event per Exotel leg that failed** — every dial attempt that missed produces its own event. Would fan out six SMSes for a three-user chain with `retry_count = 1`. **(b) One event per side** — a single anchor recipient (e.g. the assigned Technician) regardless of chain size. **(c) Fire on every leg including the answered one.** | (a) spams users and burns SMS budget; the same person gets the same alert twice if they were duplicated in the array. (b) leaves the Admin (Manager) and the CSP owner (Owner) unnotified. (c) violates the "callee missed the call" intent — the person who answered didn't miss anything. G3 was added in v0.2 to formalise the chosen scope. | 2026-09-11 |
| 5 | Behaviour when the PIN row is missing or deallocated at emit time (defensive edge) | **Suppress the emission for that callee. Log for diagnostics. Never emit an empty-PIN event.** | **Fire the event with an empty PIN field** so downstream at least knows about the miss. (Original v0.1–v0.3 model.) | A PIN-less SMS is useless — the callee cannot dial back without the PIN. In practice, a deallocated PIN would have already blocked the call from bridging, so the callee wouldn't have missed it. G4 was added in v0.4 to formalise "no event without a populated PIN". The suppression branch is defensive with a diagnostic alarm attached; if it ever fires, that's a data anomaly worth investigating. | 2026-09-11 |
| 6 | Actor framing in prose ("IVR fires the event" vs "the event fires") | **Event-side passive** — "a Missed-call event lands on CleverTap when …". Do not name a service as the actor. | Actor framing — "the IVR service fires the event …". | Keeps the language implementer-agnostic. Which service constructs the payload is a design choice for the implementer, not a PRD claim. Applied in §1, §2 and §5 prose. | 2026-09-11 |
| 7 | Whether to have per-flow ACs for the three IVR calling origins | **Yes, one AC per origin path** — AC-WF-3 (P1 in-app CTA), AC-WF-4 (P2 dialer, single active Task), AC-WF-5 (P3 dialer, PIN required). | Rely on the fact that all three paths converge at the Exotel Connect leg and let a single AC represent the enrichment behaviour. | Symmetry with the sibling IVR Retry Count PRD (which also uses per-flow ACs). Makes the cross-flow contract explicit and testable; a downstream QA can attack each path independently. | 2026-09-11 |
| 8 | Whether to keep an M-id success metric ("missed-call → successful bridged callback within 30 min") | **Drop the direct success metric from this PRD.** | Keep it with a "measure baseline before SMS goes live, target +5 percentage-point lift" note. | The end-to-end callback lift is caused by the SMS campaign (out of scope), not by the event enrichment on its own. Attaching a metric here would either overclaim (measuring downstream success against upstream ship) or duplicate what belongs to the SMS spec. The G1 broken-consumer invariant is retained. | 2026-09-11 (finalise) |
| 9 | Renumbering T- and MQ-ids at v1.0 sign-off | **Preserve T3 and T4 IDs; leave the T2 hole. Renumber MQ-1 → MQ-3 cleanly since the M1 drop broke MQ-1 anyway.** Both recorded as Overrides in v1.0. | Renumber everything so T- and MQ-ids are sequential from 0/1 (clean but ripples through all AC anchors). | The T-block had 4 IDs and many AC anchors — the ripple cost outweighed the aesthetic win. The MQ-block was smaller and MQ-1 was already going away with M1, so the renumber ripple was contained. | 2026-09-11 (finalise) |
| 10 | Re-author v1.0 in Template v5 rather than update in place | **Create parallel v2 files (`IVR_Missed_Call_Alert_PIN_PRD_v2.md`, `IVR_Missed_Call_Alert_PIN_Tradeoffs_v2.md`).** Preserve v1.0 as-is on the same repo. | **(a) In-place update** — overwrite v1.0 with v5 content. **(b) Skip the re-authoring** — v1.0 is fine, the v4→v5 delta is structural not behavioural. | The user's explicit ask was to create new files, not to touch v1.0 (signed off 11 Sep 2026). Keeping both preserves the v1.0 signed-off record and lets reviewers diff v4-vs-v5 side by side. Behaviourally the two are identical; the delta is structural (single §5 diagram, no §3b T-table, no §6 Measurement), terminological (Wiom Operational Terminology alignment: **Task** replaces "ticket" in prose; `ticket_id`, `ticket_type` and `ivr_pin_registry` stay verbatim per rule 9), and header-adding (Terminology source row). Row 8 (dropped success metric) and row 9 (T2 hole / MQ renumber) are now Overrides in v2 §Overrides — the T-hole no longer exists because a decision flowchart has no Tn ids. | 2026-09-29 |
