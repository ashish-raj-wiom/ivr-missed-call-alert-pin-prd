# IVR Missed Call Alert — PIN in Event Payload — Tradeoffs Register

Companion to `IVR_Missed_Call_Alert_PIN_PRD.md` (v1.0 · signed off 2026-09-11). Records every decided tradeoff during interview and review passes. Not part of the PRD; kept for later reference so anyone asking *"why did we pick X?"* has the answer without archaeology.

| # | Decision point | Chosen | Rejected options | Why (PM's stated reason) | Date |
|---|---|---|---|---|---|
| 1 | Scope of the change | **Narrow event enrichment only** — add `customer_pin` to `dnp_customer_missed_call_alert` and `csp_pin` to `call_dnp_missed_call_alert`; nothing else. | **(a) Full SMS-campaign PRD** — spec the SMS template, DLT copy, delivery rules and CleverTap journey inside this PRD. **(b) Add a new CT event** dedicated to callback-with-PIN. | The SMS campaign is a downstream CRM change that binds to the enriched event — separate concern, separate owner. Reusing the existing two events keeps consumer contracts intact (G1) and lets the SMS spec ship independently. | 2026-09-10 |
| 2 | Which PIN goes where | **Callee's own side** — customer's PIN on the customer event, CSP's PIN on the CSP event, sourced from the callee-side row in `ivr_pin_registry`. | **(a) Both PINs on both events** — send customer_pin AND csp_pin on both events. **(b) Caller's PIN** — send the calling side's PIN instead. | The recipient of the SMS is the callee; the PIN they need to dial back is their own. Cross-populating leaks a PIN across sides and confuses downstream binding. Caller's PIN would authenticate the wrong person. | 2026-09-10 |
| 3 | What visibility (`ivr_pin_registry.visible`) gates | **Visibility gates the CALL path (IVR vs normal), not the event payload.** If `visible = false` the call never becomes an IVR call, so these events do not exist for it. Every emission path assumes `visible = true` at call start; the flag is not re-checked at emit time. | **Visibility gates the payload** — the event fires under both `visible = true` and `false`, but the PIN field is empty when `false`. (Original v0.1 draft.) | The v0.1 model solved a case that cannot happen — IVR routing already blocks non-visible tickets from becoming IVR calls. G3 (payload-visibility guardrail), T2 (visible=false transition) and AC-VIS-1/2 were removed in v0.3. Simpler model, one fewer branch, no dead code. | 2026-09-11 |
| 4 | Recipient scope for the missed-call event across rollover + `retry_count` | **One event per registered user per call session, at end of session, only if no one answered.** Alternate/non-registered numbers never receive an event. `retry_count` duplicates in the numbers array never multiply emissions. | **(a) One event per Exotel leg that failed** — every dial attempt that missed produces its own event. Would fan out 6 SMSes for a 3-user chain with `retry_count = 1`. **(b) One event per side** — a single anchor recipient (e.g. the assigned executor) regardless of rollover chain size. **(c) Fire on every leg including the answered one.** | (a) spams users and burns SMS budget; the same person gets the same alert twice if they were duplicated in the array. (b) leaves non-anchor recipients (manager/owner) unnotified. (c) violates the "callee missed the call" intent — the person who answered didn't miss anything. G3 was added in v0.2 to formalise the chosen scope. | 2026-09-11 |
| 5 | Behaviour when the PIN row is missing or deallocated at emit time (defensive edge) | **Suppress the emission for that callee. Log for diagnostics (MQ-1). Never emit an empty-PIN event.** | **Fire the event with an empty PIN field** so downstream at least knows about the miss. (Original v0.1–v0.3 model, R2/T3.) | A PIN-less SMS is useless — the callee cannot dial back without the PIN. And in practice, a deallocated PIN would have already blocked the IVR call from bridging, so the callee wouldn't have missed it. G4 was added in v0.4 to formalise "no event without a populated PIN." T3 is now a defensive branch with an alarm attached; if it ever fires, that's a data anomaly worth investigating. | 2026-09-11 |
| 6 | Actor framing in prose ("IVR fires the event" vs "the event fires") | **Event-side passive** — "a missed-call alert event gets fired on CleverTap when …". Don't name IVR as the actor. | Actor framing — "the IVR service fires the event …". | Keeps the language implementer-agnostic. Which service constructs the payload is a design choice for the implementer, not a PRD claim. Applied to §1 Context, §1 Boundary, §8 Glossary at the same time. | 2026-09-11 |
| 7 | Whether to have per-flow ACs for the three IVR calling origins | **Yes, one AC per origin path** — AC-WF-3 (P1 in-app CTA), AC-WF-4 (P2 dialer + single active ticket, no PIN), AC-WF-5 (P3 dialer + PIN required). | Rely on the fact that all three paths converge at the Connect leg and let a single AC represent the enrichment behaviour. | Symmetry with the sibling `ivr-retry-count-prd` (which also uses per-flow ACs). Makes the cross-flow contract explicit and testable; a downstream QA can attack each path independently. | 2026-09-11 |
| 8 | Whether to keep the M1 success metric ("missed-call → successful bridged callback within 30 min") | **Drop M1 entirely. This PRD has no direct success metric.** Recorded as an Override. | Keep M1 with a "measure baseline before SMS goes live, target +5pp" note. | The end-to-end callback lift is caused by the SMS campaign (out of scope), not by the event enrichment on its own. Attaching a metric here would either overclaim or duplicate what belongs to the SMS spec. The G1 broken-consumer invariant is retained instead. | 2026-09-11 (finalise) |
| 9 | Tradeoff between renumbering T2/T3/T4 for stable IDs vs preserving legacy IDs at sign-off | **Preserve T3 and T4 IDs; leave the T2 hole. Renumber MQ-1 → MQ-3 cleanly since the M1 drop broke MQ-1 anyway.** Both recorded as Overrides. | Renumber everything so T-ids and MQ-ids are sequential from 0/1 (clean but ripples through all AC anchors). | The T-block has 4 IDs and many AC anchors — the ripple cost outweighs the aesthetic win. The MQ-block is smaller and MQ-1 was already going away with M1, so the renumber ripple was contained. | 2026-09-11 (finalise) |
